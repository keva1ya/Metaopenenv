# Metaopenenv Security Architecture

This document details the end-to-end security measures implemented in the Metaopenenv architecture. It covers how the system protects its APIs, user interfaces, data, and Large Language Models (LLMs) from common vulnerabilities and adversarial attacks.

---

## 1. API Security (FastAPI)

The FastAPI backend (`app.py`) is secured against unauthorized access, abuse, and malformed data.

*   **Authentication & Authorization:**
    *   All core endpoints (`/step`, `/reset`, `/state`) are protected by API key authentication.
    *   Clients must provide a valid key via the `X-API-Key` HTTP header.
    *   The expected key is securely loaded from the `APP_API_KEY` environment variable. If this variable is not set, authentication is bypassed (useful for local development, but must be set in production).
*   **Rate Limiting:**
    *   The `slowapi` library is used to prevent brute-force attacks and control costs (especially for LLM-heavy routes).
    *   Limits are applied per IP address:
        *   `/step`: 30 requests per minute.
        *   `/state` & `/health`: 60 requests per minute.
        *   `/reset`: 10 requests per minute.
*   **Input Validation:**
    *   The `/step` endpoint uses a strict Pydantic model (`StepRequest`) to validate incoming payloads.
    *   It ensures that only valid `LoanAction` enums (e.g., `APPROVE`, `REJECT`, `REQUEST_MORE_INFO`) are accepted, preventing arbitrary data injection or malformed requests from crashing the engine.
*   **CORS (Cross-Origin Resource Sharing):**
    *   `CORSMiddleware` is explicitly configured. In production, the `allow_origins` list should be restricted to trusted domains (e.g., the specific URL where the frontend is hosted) rather than the default `["*"]`.

---

## 2. UI Security (Gradio)

The interactive Gradio dashboard is protected from unauthorized access.

*   **Basic Authentication:**
    *   The Gradio UI requires a username and password to access the dashboard.
    *   Credentials are securely loaded from the `APP_UI_USERNAME` and `APP_UI_PASSWORD` environment variables.
    *   If these variables are not set, the UI launches without authentication (for local dev only).
*   **Network Exposure:**
    *   By default, the UI binds to `127.0.0.1` (localhost) and sets `share=False`. This ensures the dashboard is not accidentally exposed to the public internet via Gradio's public sharing feature.

## 3. LLM & Prompt Security

This is the most critical attack surface in a multi-agent system. Metaopenenv employs several layers of defense against prompt injection and adversarial manipulation.

*   **Prompt Isolation (XML Delimiters):**
    *   Instructions are strictly separated from untrusted data in the system prompts for the Head Agents (`RiskAgent`, `FraudAgent`, `PolicyAgent`).
    *   Untrusted data (applicant metrics, sub-agent reports, and dissent history) is wrapped in explicit XML-style tags (e.g., `<applicant_data>`, `<sub_agent_reports>`, `<dissent_history>`).
    *   This structural separation helps the LLM distinguish between the system's core instructions and the data it is evaluating, significantly reducing the success rate of prompt injection attacks hidden within applicant data.
*   **Feedback Loop Sanitization (Defeating Indirect Prompt Injection):**
    *   The system logs dissenting votes and their reasoning. This reasoning (generated by an LLM) is later fed back into the prompt as `dissent_history` for future episodes.
    *   To prevent a compromised LLM from injecting malicious instructions into future episodes (indirect prompt injection), the `VotingEngine` sanitizes the `dissent_reason` before logging it.
    *   **Length Capping:** The reasoning is hard-capped at 250 characters to prevent buffer overflow or excessively long injection payloads.
    *   **Keyword Stripping:** A regex filter actively strips out common injection vectors and structural tags (e.g., "ignore previous instructions", "system:", `<applicant_data>`) and replaces them with `[REDACTED]`.
*   **Deterministic Fallbacks:**
    *   If an LLM endpoint fails, times out, or returns an unparseable response, the agents immediately fall back to deterministic, rule-based logic (e.g., majority voting or soft aggregation).
    *   This ensures the system fails safe and cannot be forced into an undefined state by an attacker manipulating the LLM endpoint.

---

## 4. Secrets Management

*   **Environment Variables:**
    *   No API keys, Hugging Face tokens, or UI credentials are hardcoded in the source code.
    *   All secrets are loaded dynamically via `os.getenv()` or the `python-dotenv` library.
*   **Git Ignore:**
    *   The `.env` file is explicitly listed in `.gitignore` to prevent accidental commits of sensitive credentials to version control.

---

## 5. Data Privacy & Integrity

*   **Synthetic Data (Current State):**
    *   The current implementation uses synthetic data generated by `SyntheticDataGenerator`. The `LoanObservation` schema does not contain direct Personally Identifiable Information (PII) like names, SSNs, or phone numbers.
*   **Production Considerations (Future State):**
    *   If real applicant data is introduced, a sanitization/masking layer must be added before data is passed to the LLMs or logged to the `TraceBuffer`.
    *   The `logs/rl_trace.jsonl` and `logs/dissent_log.json` files contain sensitive financial profiles and model reasoning. In a production environment, these files must be encrypted at rest and subject to strict file-system access controls.
